Abstract. This study presents the design, implementation, and evaluation of a
novel web-based Ground Control Station (GCS) application for real-time
monitoring of quadcopter Unmanned Aerial Vehicles (UAVs). The research
addresses the operational limitations of traditional desktop-based GCS
applications, such as platform dependency, installation overhead, and specific
hardware driver incompatibilities, which hindered a previous C# application
from reading flight controller communication ports and accurately visualizing
UAV positions. To overcome these challenges, this work introduces a cross-
platform, browser-accessible GCS developed using a full-stack JavaScript
architecture, featuring Node.js for the backend and React.js for the frontend.
Real-time, low-latency data streaming is achieved through a persistent
WebSocket connection, managed by Socket.IO, which processes telemetry data
from the flight controller via the MultiWii Serial Protocol (MSP). The system
was developed using the Prototype method to ensure continuous alignment with
user needs. Performance evaluation under controlled indoor conditions
demonstrated an average end-to-end data transmission latency of 48.5 ms, a
stable data refresh rate of 19.8 Hz, and a mean positional accuracy of ±1.2 m.
The GCS application effectively displays critical sensor data-including pitch,
roll, yaw, battery status, and UAV position on a digital map accurately and in
real-time. This application offers a flexible, accessible, and efficient GCS
alternative for UAV developers and is expected to support the Barelang Force
2.0 Team in the Indonesian Flying Robot Contest (KRTI).
Keywords: Ground Control Station; Quadcopter; Unmanned Aerial Vehicle;
Real-Time Monitoring; Prototype Development.

significantly, with the quadcopter emerging as one of the most versatile and widely
deployed platforms for applications ranging from aerial mapping to search-and-rescue
missions. Central to the safe and effective operation of any UAV is the Ground Control
Station (GCS), which serves as the command hub for monitoring the vehicle's flight
status and receiving real-time telemetry data. An effective GCS is paramount for
ensuring mission success and enhancing operational safety. This research is directly
motivated by the challenges faced within the framework of the Indonesian Flying Robot

2.2. Software Architecture and Data Flow
The software architecture is designed as a modem, three-tierweb application. It consists
of the data source (UAV Flight Controller), a backend server (Node.js), and a frontend
client (React.js). This architecture was chosen to decouple the hardware interface from
the user interface, promoting modularity and scalability.
2.2.1. Data Acquisition and Communication Protocol (Backend)
The foundation of the data pipeline is the communication between the flight controller
and the backend server. The flight controller transmits telemetry data using the Multi-
Wii Serial Protocol (MSP), a lightweight, binary message-based protocol designed for
efficient communication over serial links. MSP is supported by a variety of flight con-
troller finnwares, including Betaflight, iNav, and ArduPilot (for OSD and telemetry
functions), making it a versatile choice.

The backendis implemented in Node.js, a JavaScript runtime environment chosen for
its asynchronous, non-blocking 1/0 model, which is highly suitable for handling real-
time data streams from hardware devices. The serialport hbrary is utilized to establish
a connection with the flight controller's virtual COM port via USB at a baud rate of
115200[9].
Upon connection, the backend begins listening for incoming data. It implements a par-
ser that processes the raw binary stream from the serial port. The parser identifies the
MSP message structure, which consists of a preamble ('$M<'), a direction indicator,
payload size, message ID, the payload itself, and a checksum. The backenddecodes the
binary payload based on the message ID (e.g., MSP_ATTITUDE, MSP_RAW_GPS}
into meaningful numerical values. These parsed values are then structured into a stand-
ardized JSON (Java Script Object Notation) format, making the data easily consumable
by any web client [10].
2.2.2. Real-Time Data Streaming (Backend to Frontend}
To achieve real-time data visualization, a persistent, low-latency communication chan-
nel between the backend and frontend is essential. Traditional HTTP-based REST
APis, which operate on a request-response model, are ill-suited for this purpose. An
HTTP polling approach, where the client repeatedly requests updates from the server,
would introduce significant latency and network overhead from the continuous setup
and teardown of TCP connections and redundant HTTP headers for each request.
This system instead employs the WebSocket protocol, which provides a full-duplex
communication channel over a single, long-lived TCP connection. This allows the
server to "push" data to the client the instant it becomes available, drastically reducing
latency and overhead. The implementation uses the Socket.IO library, which provides
a robust abstraction over WebSockets with features like automatic reconnection and
event-based communication. Once the Node.j s backend parses a new MSP messag;: and
converts it to JSON, it immediately emits this data object over the Web Socket channel
to all connected frontend clients [11].
2.2.3. Data Visualization (Frontend)
The frontend client is a Single-Page Application (SPA) built with React.js, a popuhr
JavaScript hbrary for building dynamic and interactive user interfaces. Its component-
based architecture allows for the modular development ofUI elements, each responsi-
ble for displaying a specific piece of telemetry data.
The client uses the socket.io-client hbrary to establish a connection to the backend
server and listen for incoming data events. When a new telemetry packet is received,
the application's state is updated, and React efficiently re-renders only the components
that have changed [12]. This ensures a smooth and responsive user experience. Key
visualization components include:

2.3 Software Development Method
The development of this GCS application followed the Prototype Model. This software
development lifecycle model involves creating an initial, functional version of the sys-
tem (a prototype), which is then evaluated by users to gather feedback for subsequent
refinement and iteration.
While other methodologies like Waterfall and Agile are common, the Prototype model
was specifically chosen for several reasons pertinent to this project's context. The Wa-
terfall model, with its rigid, sequential phases and requirement for a complete, upfront
definition of all system specifications, is unsuitable for research and development pro-
jects where requirements are often discovered and refined through experimenta-
tion. The primary stakeholder for this GCS is a competitive robotics team whose needs
evolve based on competition rules, field testing, and iterative hardware changes [13].
Agile methodologies, while iterative, are typically structured around sprints aimed at
delivering discrete, pre-defined features from a product backlog. The Prototype model,
in contrast, is better suited for the initial, exploratory phase of this project. The primary
goal was notto deliver a set of features, butto quickly build a working system to vali-
date the core technical concept the viability ofa web-based GCS and to use this tangible
prototype as the primary tool for eliciting detailed requirements and usability feedback
from the end-users (the BarelangForce 2.0 team). This iterative feedback loop, centred
on a working model, ensures the final product is closely aligned with user needs and is
more effective for requirement discovery in an R&D setting than the more structured
approaches of Waterfall or Agile.

The gyroscope is a sensor designed to measure changes in position or object rotation in
three-dimensional space. This technology is used to ensure accurate orientation in
UAVs, avoid electromagnetic interference that could affect other sensor performance,
and maintain stability during operation-particularly in applications requiring high pre-
cision, such as navigation systems and augmented reality [17]. The accelerometer is
used to measure linear acceleration, and in the context of UAVs, it helps determine
angularposition by detecting acceleration due to gravity. However, its main challenge
is measurement noise, which can affect accuracy. To address this, accelerometer data
is often processed using digital filters such as the Kalman filter or complementary filter
to enhance angular estimation accuracy [12]. The magnetometer, as a magnetic field
sensor, improves navigation accuracy by detecting the Earth's magnetic field, which is
critical for UA V orientation and positioning. Magnetometers are often integrated with
the Inertial Measurement Unit (IMU) to provide more accurate data, especially when
GPS signals are disrupted [18]. The barometer is employed to measure atmosphere
pressure and is crucial in UAV flight systems. By measuring air pressure, the barometer
can determine UAV altitude and help maintain flight stability even in environmental
conditions such as wind. Barometric sensors like the BME280 are commonly used to
ensure UAVs follow programmed flight paths accurately [14].

3.2 Experimental Setup and Performance Evaluation
3.2.1. Test Environment and Scenarios
To validate the functionality and performance of the developed GCS, a series of struc-
tured tests were conducted. All tests took place on June 18, 2025, within the open Field
at Politeknik Negeri Ba tam. This environment provided a controlled space ofapproxi-
mately40m x 20m, free from wind and potential GPS signal interference, ensuring that
external variables did not impact the measurements. The GCS was connected directly
to the quadcopter'sflight controller via a USB cable to guarantee a stable, high-band-
width communication link, thereby isolatingtheperformance evaluation to the software
system itself.
A series of black box tests were designed to verify that each functional requirement of
the system operated as specified. These tests were executed manually by an operator
interacting with the GCS interface. The test cases included:
a) Scenario 1 (Connectivity): Verifying the system's ability to correctly list avail-
able serial ports, establish a connection atthe specified 115200 baud rate, and
cleanly terminate the connection.
b) Scenario 2 (Static Data Display): With the UAV stationary and disarmed on
the ground, verifying that all sensor status indicators showed a valid state (e.g.,
green) and that initial values for attitude, battery, and GPS were displayed
correctly and without error.
c) Scenario 3 (Dynamic Data Update): Manually tilting the UAV along its pitch
and roll axes to simulate flight dynamics. The test verified that the attitude
indicators, heading display, and graphical charts on the GCS updated in real-
time, reflecting the correct direction and magnitude of the motion.

3.2.2. Performance Metrics and Measurement Techniques
To move beyond descriptive claims and provide a rigorous, quantitative evalua fon of
the system, the following Key Performancelndicators(KPis) were defined and meas-
ured.
a) Data Transmission Latency(ms): This metric quantifies the delay in the com-
munication channellt was measured as the round-trip time (RTT) ofa Web-
Socket ping-pong exchange. The Node.js backend was configured to send a
timestamped ping frame every second; the React.js frontend was programmed
to immediately respond with a pong frame upon receipt. The backend then
calculated the latency as the time difference between sending the ping and
receiving the corresponding pong. This method provides a reliable proxy for
the latency of the underlying communication channel [18].
b) Data Refresh Rate (Hz): This metric measures the frequency of telemetry up-
dates received by theuserinterface. It was calculated on the frontend by count-
ing the numberoftelemetry data packets received via Web Socket per second.
The mean and standard deviation were computed over the 120-second test pe-
riod to assess the rate and stability of the data stream.
c) PositionalAccuracy(m): This metric evaluatestheaccuracyoftheGCS'smap
visualization. It was calculated as the Euclidean distance between the GPS
coordinates (latitude, longitude) reported by the GCS and the pre-measured
ground-truth coordinates of the physical markers used in Scenario 5. This
quantifies the real-world error of the displayed position.
d) GCS Resource Consumption: To assess the efficiency of the web application,
its impact on the client machine was measured. Using the Google Chrome
browser's built-in developer tools (Performance tab), the average CPU utiliza-
tion(%) and memory footprint (MB) of the GCS browser tab were recorded
during the 120-second test run of Scenario 4.

4 Conclusion
This study successfully demonstrated the design, development, and validation of a web-
based Ground Control Station for the real-time monitoring of quadcopter UAVs. By
leveraging a full-stack JavaScript architecture with Node.js, React.js, and Web Sockets,
the research effectively addressed the platform-dependency and hardware-interfacing
limitations of a previous desktop-based application. The developed system provides a
responsive, cross-platform, and zero-installation solution that is accessible from any
modern web browser.
The quantitative performance evaluation confirmed the viability of this web-based ap-
proach for time-sensitive applications, achieving an average data transmission latency
of under 50 ms and a stable data refresh rate of approximately 20 Hz, all while main-
taining minimal resource consumption on the client device. The novelty of this work
lies in its architectural choice, which fills a gap in the existing GCS ecosystem by pri-
oritizing accessibility and ease of deployment over the comprehensive but complex
feature sets of traditional desktop-native applications like Mission Planner and
QGroundControl. While the current implementation is limited to monitoring, it estab-
lishes a robust and scalable foundation for future development This web-based GCS is
expected to serve as an adaptive and reliable tool that supports the advancement of
UAV technology, particularly for academic research, educational purposes, and com-
petitive teams such as the Barelang Force 2.0.
